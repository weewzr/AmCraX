# AmCraX known limitations

Organised by layer. Each item states the consequence and a suggested remedy. Sources: module docstrings, `backend/amcrax/data/*.yaml`,
`docs/validation/discrepancy_analysis.md`, and `results/validation/validation_matrix.json` (status values `pass`, `fail`, `not_run`,
`informational`). The matrix is regenerated by `scripts/build_validation_matrix.py`; this file does not quote counts, so read the matrix for the current state (dashboard page "Validation",
[validation/validation_matrix.md](validation/validation_matrix.md)). At the time of writing the failing items fall into two groups: the `FS-<case>` flowsheet cross-checks and the
`KIN-NI-PRED` and `KIN-RU-PRED` kinetics items (sections 2 and 5). Items found in code review that remain open are in section 10. Assumption values are in [model_assumptions.md](model_assumptions.md).

## 1. Platform and operation

| Limitation | Consequence | Remedy |
|---|---|---|
| Windows only; Aspen automation uses COM (`pywin32`) and Windows file locks (`msvcrt`) | The live Aspen path does not run on Linux / macOS | Use stored results + Python model there; a cross-platform automation layer would be new work |
| Needs a licensed Aspen Plus V15 for any live simulation | Without it the dashboard offers only stored Aspen results and the Python model (SNAPSHOT / `python_model`); the API answers 503 `aspen_unavailable` and never substitutes Python for an Aspen request | Provide a licence; for reviewers use the exported snapshot |
| Single Aspen seat, jobs strictly serial | A second Aspen job waits (queued) behind a machine-wide lock `aspen/runs/.aspen.lock`; waiting counts toward the 600 s job time-out | Raise `AMCRAX_ASPEN_TIMEOUT_S`; use a pool of licences and workers if throughput matters |
| Development servers only: Vite dev server and uvicorn, **no authentication**, no HTTPS, CORS restricted to localhost:5173 | Must not be exposed to a network; anyone who reaches the API can run jobs and delete user (python) cases | Put behind an authenticated reverse proxy and a production build (`npm run build`) before any shared deployment |
| In-memory, unbounded job queue | Jobs are not limited in number (a flood of submissions queues without bound); a restart of the API (also by `uvicorn --reload` or the dev supervisor on a code save) abandons queued / running jobs; they are later reported `failed` | Run Aspen jobs against a server without reload; persist the queue if needed |
| Aspen worker time-outs kill the process tree | An `AspenPlus.exe` can be orphaned; cleaned up only on the next AmCraX Aspen run (`kill_orphaned_sessions`). The Aspen pid is inferred from a process-list difference, which can be wrong if another Aspen is started at the same moment | End the process manually if needed (docs/installation.md); do not start other Aspen sessions during an AmCraX run |
| Research PDFs are excluded from version control | Readers do not receive the copyrighted papers; extracted text under `research/extracted/` is also git-ignored | Obtain the papers from the publishers; the citation list is `research/references.json` |
| Report / deck PDF export needs Microsoft Word / PowerPoint COM; report needs pandoc | Rebuilding the PDFs is impossible without Office | Use the committed PDFs; the `.docx` / `.pptx` build without Office up to the export step (`--no-pdf` for the report) |
| Frontend tests and screenshots are not part of `pytest` | Frontend regressions need `npm test` and `npm run build` | Run them before a release |
| Aspen records the Windows user and host names inside solved files | The `.bkp` files in `aspen/models/` are sanitised by `aspen/automation/sanitise_models.py`; `.apw` documents embed the same names and are not version-controlled. The run-status screenshot in `aspen/screenshots/` is masked | Run `sanitise_models.py` after any run that rewrites a `.bkp`; mask the user and host fields of any new run-status capture |

## 2. Flowsheet and thermodynamics

| Limitation | Consequence | Remedy |
|---|---|---|
| Equilibrium reactor (RGibbs): no kinetics, catalyst or approach to equilibrium | Conversion is an upper bound at given T and P; real conversion depends on catalyst mass and kinetics | Use the PFR section (Reactor Analysis) for catalyst-specific estimates, with the caveats in section 5 |
| Single net reaction; no side reactions; NOx / N2O not modelled | Combustion and any nitriding / hydrazine paths ignored | Extend component and reaction sets if relevant |
| Steady state only | No start-up, shut-down, turn-down, or dynamics | Dynamic model is out of scope |
| Fixed pressure profile (`inp_writer.DP`), valid for P >= 3 bar | Pressure drops are not computed from equipment design | Replace with sized equipment pressure drops |
| No NH3 polishing unit | The product hydrogen is not shown to meet a fuel-cell NH3 limit (0.1 ppm quoted in `separation.yaml`); TSA / membrane polishing is only literature context | Add a polishing unit (TSA or membrane) to the flowsheet |
| No cracked-gas compression in the Aspen flowsheet | The PSA operates at cracker pressure (reactor P - 1.5 bar); literature PSA feed requirement is 7 bar. The Python optimisation evaluator adds compression power outside Aspen (`optimisation/evaluate.py`) | Add a compressor block to the Aspen model |
| Fixed feed (99.8 / 0.2 mol% NH3/H2O), 100 kmol/h, air at 25 degC | Other feed qualities need new inputs / possibly a new input file | Parameterise via `CaseInputs` |
| Python feed-section model vs Aspen PENG-ROB: the 20 flowsheet cross-check items `FS-<case>` fail (vaporiser, exchanger and cooler duties 3-10 % apart; the Python vaporiser dew point uses an ideal liquid / Raoult and is about 5.8 K below PENG-ROB, and liquid-NH3 enthalpy comes from the CoolProp reference EOS). The `FS-PRIMARY-<case>` family (conversion, product flow, reactor duty, ...) passes for all 20 cases | The Python model is a cross-check and surrogate, not an Aspen replacement; individual feed-section duties from it carry a 3-10 % model-form difference. Documented model-form difference, not a data error | Compare with `eos="pr"` results; do not tune. Detailed rows in `results/validation/aspen_vs_python_flowsheet.csv` |
| Python equilibrium vs Aspen: 1.48 pp maximum with PENG-ROB vs ideal; ideal-vs-ideal 0.045 pp (`docs/validation/discrepancy_analysis.md`) | Explained (fugacity coefficients and a 10-12 J/mol standard-state data offset); not an error | None; compare like with like (Aspen IDEAL vs Python ideal, Aspen PENG-ROB vs Python PR) |
| Equilibrium enthalpy check `EQ-DH-ASPEN` (resolved): an earlier anomalous Aspen duty at 600 degC, 30 bar was a stale-value defect of the automation, found by this validation and fixed (synchronous runs, regenerated grid with repeatability and stale-value checks; `docs/validation/discrepancy_analysis.md`). It now passes | None outstanding; any new Aspen grid must keep the repeatability and stale-value checks | Re-run `aspen/automation/run_equilibrium_grid.py` when the automation changes |
| Peng-Robinson k_ij = 0 in the Python model | Aspen PENG-ROB (retrieved kij) vs Python PR differ by up to 0.185 pp conversion | Source binary parameters |
| The FEHE feasibility guard (`amcrax.aspen.inp_writer.fehe_cold_outlet_minimum_C`) depends on pressure: ammonia saturation temperature at the vaporiser outlet plus the vaporiser superheat plus a 25 K margin | A screening estimate of whether the cold outlet lies above the vaporiser outlet, not a heat-exchanger design. If CoolProp is unavailable it falls back to a fixed 120 degC | Replace by a rigorous check against the solved vaporiser outlet |

## 3. Heat integration

| Limitation | Consequence | Remedy |
|---|---|---|
| Overall U = 50 W/(m2 K) assumed (range 10-100) | FEHE area is order-of-magnitude only; duties are unaffected | Size the exchanger with a design correlation |
| Exchanger pressure drops neglected for enthalpy; water latent heat neglected | Small | - |
| Pinch targets are thermodynamic targets, not a designed heat-exchanger network | No network, no utility system, no flue-gas duct design | Network synthesis would be a separate study |

## 4. Purification

| Limitation | Consequence | Remedy |
|---|---|---|
| Reduced-order PSA (component splitter with recovery and N2 slip) | No beds, cycles, adsorbent, purge, pressure-swing energy, or purity-recovery trade-off. The baseline recovery 0.85 is above every literature value quoted (0.71-0.81) | Replace by Aspen Adsorption or a detailed model; keep literature points as bounds |
| Membrane model: Sieverts flux law, infinite selectivity, concentration polarisation not applied by default, no module design | Optimistic purity; the polarisation multiplier is ambiguous in the source | Use the explicit `flux_multiplier` for sensitivity |
| One permeability set of three is unusable (misprinted pre-exponential) | Only two sets drive the model | Verify the original source |

## 5. Kinetics and PFR

| Limitation | Consequence | Remedy |
|---|---|---|
| Takahashi kinetics fitted at **1 atm** (X < 20 %), Kum fit up to 10 bar; used at 20 bar | Unvalidated extrapolation; PFR results are `python_model` estimates, not predictions | Fit / validate against high-pressure data |
| Kinetic validation items `KIN-NI-PRED` and `KIN-RU-PRED` fail: maximum absolute conversion deviation about 0.11 vs a tolerance of 0.05 (6 of 12 and 6 of 11 digitised points outside tolerance); contact time (W/F) was inferred from one anchor point | The model does not reproduce the published curves to the set tolerance; limits the confidence in the catalyst mass estimates | Obtain the catalyst mass / contact time from the source or re-fit; do not loosen the tolerance |
| Equilibrium approach factor (1 - Q/Kp) is an AmCraX extension | Prevents conversion above equilibrium but is not part of the published model | Replace with reversible elementary steps |
| PFR neglects intraparticle diffusion, film transfer, radial gradients, dispersion, deactivation | Over-predicts conversion per kg catalyst for real pellets | Add effectiveness factors / 2-D model |
| Kinetics are catalyst-specific (Ni/MgO, Ru/MgO, Ru/Al2O3) | The flowsheet's equilibrium cracker is catalyst-agnostic | - |

## 6. Techno-economics

| Limitation | Consequence | Remedy |
|---|---|---|
| Plant-level CAPEX correlation (`ahmad2025gtcc`, Fig. 6) | Order-of-magnitude (class 4-5) estimate; no equipment list or sizing | Build an equipment-based estimate |
| Mixed cost years (2024, 2025, not stated); no CEPCI escalation (library values conflict) | LCOH is "mixed 2024-2025 USD" | Resolve CEPCI and escalate |
| Labour on an India small-plant basis; catalyst inventory from literature space velocity | Not site-specific | Provide site data |
| Imported heat priced as burnt NH3 at 100 % LHV efficiency; surplus heat not credited | Fuel cost is a lower bound | Lower `ammonia_fuel_heat_efficiency` |
| AmCraX LCOH is below the literature LCOH it is compared with (the literature benchmark rows of `results/validation/literature_benchmarks.csv` and the economics defaults list the values) | Reported, not tuned. Likely drivers: simplified CAPEX, 100 % heat efficiency, no compression, no hydrogen delivery, and no NOx treatment or NH3 polishing | Investigate before quoting an absolute LCOH; use relative comparisons |
| The ammonia feed is priced on its contained NH3; the feed water is not priced | This is the current basis, shared with the carbon-intensity module. Earlier results that priced the whole feed stream as ammonia overstated the feed cost by the water mass fraction | Regenerate stored economic results after pulling this change (`scripts/run_economics.py`) |
| Compression power is zero unless supplied | LCOH understated when PSA feed pressure is below the requirement | See `optimisation/evaluate.py` for the Python-side correction |

## 7. Carbon intensity

| Limitation | Consequence | Remedy |
|---|---|---|
| Simplified accounting, not an LCA: activity data x literature factors | Boundary excludes equipment manufacture, upstream natural-gas methane leakage, N2O / NOx, boil-off, port handling | Use an LCA tool for any compliance claim |
| Green NH3 factor 0.0 only because the source excludes manufacture | Understates renewable NH3 | Use a cradle-to-gate factor |
| Shipping distance 5000 km is an assumption; GLEC factor is generic (not ammonia-specific) and taken from a secondary listing | Transport term is indicative | Provide route data |
| Grid factor (EMA) and EU RFNBO numbers were taken from search-engine extracts of script-rendered pages | Flagged in the dashboard "to be verified against primary source" | Verify against the primary documents |

## 8. Optimisation and scenarios

| Limitation | Consequence | Remedy |
|---|---|---|
| Optimisation runs on the Python model and is bounded to the Aspen-simulated ranges | The optimum is a surrogate result. The reported candidates (exact optima plus Pareto points) are re-solved in Aspen Plus V15 and compared on the primary metrics; the outcome, the tolerance and the deviations are in `results/optimisation/aspen_verification.json`, and secondary deviations are reported, not judged. Points other than the verified candidates are unverified | Run `aspen/automation/verify_candidates.py` for any new optimum |
| Solver is differential evolution + SLSQP with a fixed seed; the conversion constraint 0.95 is a design assumption | Global optimality not proven; result depends on the constraint set | Report constraint sensitivity (`results/optimisation/*.json`) |
| Scenario analysis mixes stored Aspen results (where converged) with Python results | Provenance varies per row; always read the badge | - |

## 9. API and dashboard

| Limitation | Consequence | Remedy |
|---|---|---|
| Tests that read result files (`tests/test_api.py`) can fail while those files are being rewritten by a script | Intermittent failure during result generation only | Re-run the suite and the validation matrix after generating all results |
| Dashboard PFD stream routing is hand-coded for the baseline topology (other streams use a generic elbow) | Layout of unusual topologies may be untidy | See `frontend/README.md` |
| SNAPSHOT mode disables everything that needs the API | No simulation, live sweep or optimisation in SNAPSHOT | Start the API |

## 10. Open findings from code review

Code review found several issues. Those that were fixed are not repeated here. The thermodynamics and process-model code and the API security beyond the fixed items have had no independent review.

| Limitation | Consequence | Remedy |
|---|---|---|
| Orphan-process detection infers the Aspen pid from a process-list difference | May miss or mis-select a process if another Aspen starts concurrently | Capture the pid from the COM server |
| Unbounded Aspen job queue | See section 1 | Bound the queue |

Fixed after review: the economics module prices the feed on its contained NH3 (section 6); the KPI `tailgas_combustion_heat_kW` is `max(-Q_FLUEHX, 0)`, which is the heat released by the flue gas and is zero if the flue-gas cooler would need heating; and the FEHE feasibility guard is pressure dependent (section 2).

## 11. Research expansion (Singapore hypothesis tests)

Added on 2026-11-23. The full per-workstream account, with what was validated, what failed and why, is in [research/validation_and_limitations.md](research/validation_and_limitations.md); the aggregated failures are in [validation/research_validation.md](validation/research_validation.md). The earlier sections still apply. The roadmap item "an Aspen Plus RPlug reactor using the implemented kinetics" is now available as an option for the research cases; the baseline flowsheet is still the equilibrium (RGibbs) cracker.

| Limitation | Consequence | Remedy |
|---|---|---|
| Ni/CeO2, Ru/CeO2 (Lucentini et al., 2019) have no published rate law, and Ru-K/CaO (Sayas et al., 2020) could not be read in full | These catalysts, which were priority catalysts, are not modelled; no parameter was derived from conversion points; the essay values for Ru-K/CaO are unverified | Obtain the Sayas 2020 full text and rate data for the Ni-Ru and Ru ceria catalysts |
| Rate laws are extrapolated from 1 atm (Takahashi, Lucentini) or up to 10 bar (Kum) to 20 bar | Conversion and catalyst mass at 20 bar are less certain than the Aspen and Python agreement suggests, because both use the same law | Kinetic data at 10 to 20 bar |
| Ni/MgO and Ru/MgO use a fitted LHHW approximation of the Takahashi law (RMS rate error 12 %, maximum about 50 %), valid at 20 bar only | Results for these two catalysts are labelled `python` approximation, not literature | A user kinetics subroutine (needs a Fortran compiler) |
| `KIN-NI-PRED` and `KIN-RU-PRED` still fail (about 0.11 against 0.05) | Takahashi curves are reproduced only approximately | See section 5 |
| Effectiveness factor 1 and no pressure drop in the kinetic studies | Catalyst masses are lower bounds | Add an effectiveness factor and an Ergun pressure drop to the cost comparison |
| The CAPEX model does not respond to temperature, pressure, reactor volume or exchanger area | A capital advantage or penalty of the operating temperature cannot be shown; the catalyst volume scaling is a sensitivity only | Equipment-level costing with sized units |
| Catalyst prices are proxies (Cho et al., 2026 Ni and Ru, 2-year life); no sourced price exists for Ni-Ru/CeO2 | Catalyst cost conclusions rest on a break-even price, not a price | Vendor prices for the actual catalysts |
| Python FEHE recovered heat is 3.6 to 4.4 % above Aspen (5 items fail a 3 % tolerance) | Absolute duties from the Python flowsheet carry a systematic offset; catalyst-to-catalyst differences are affected less | Use Aspen duties or align the property basis |
| LHHW runs can sit up to 4.9e-4 in conversion above the RGibbs equilibrium of the same model (3 items fail a 1e-4 tolerance) | Conversion at 40 bar is slightly optimistic | Use fugacity-based equilibrium constants in the reverse term |
| Purification: only two PSA recovery and purity points; recovery at 99.97 % H2 is bounded, not computed; membrane H2/N2 selectivity is taken as infinite in the base case; TSA, housing, skid and compression CAPEX are not modelled | The PSA trade-off is not quantified from data; membrane costs are lower bounds; only the index, total, NH3, N2 and H2O of ISO 14687 are evaluated | Adsorption-cycle simulation and membrane module data |
| No product is called fuel-cell grade; the Aspen baseline H2PROD contains about 392 ppm N2, above the Grade D limit of 300 ppm | The baseline meets an industrial 99.9 % grade only | A polishing and purification design |
| Economics use secondary web values for the blue ammonia price, exchange rate, hydrogen benchmarks and electricity; no Singapore gas price, WACC, labour rate or location factor; N2O not quantified | Absolute LCOH in Singapore has wide uncertainty (Monte Carlo grey p5 to p95 2.85 to 4.43 USD/kg in `results/research/singapore/monte_carlo.json`) | Official price and tariff data |
| Halim et al. (2025) and Deka et al. (2025) could not be read in full | The essay figures taken from them (60.1 MW, 15.1 and 10.1 USD/kg, 40 %, 81 % PSA recovery, 5.21 to 3.58 USD/kg) are unverified | Obtain the full texts |
| LCA uses unsourced scenario distances (5000 km baseline), a parameterised boil-off of zero, and low-confidence factors for coal ammonia, SMR with CCS and methane leakage | Break-even emission intensities are scenario results, not measurements | Sea-distance and leakage sources |
| The end-use and life-cycle packages are not wired into the API or the dashboard | They run from scripts only | Add endpoints and pages |
